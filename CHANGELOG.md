# Changelog

Versions are `MAJOR.MINOR.FIX`; see [docs/VERSIONING.md](docs/VERSIONING.md). Newest first.

## Unreleased (notes in the tree; a note takes the edited mark off; the edited dots stay)

- **Each chapter in the tree shows how many open notes it has**, in red, between its title and its word count. Notes by you, by an AI through the MCP server, and notes that came from another device are all counted; a chapter with none shows nothing.
- **A note on a chapter marked as edited takes the mark off, without asking.** It happens when you add a note in Write and when an AI adds one with `add_notes` (the tool's result says `editedMarkRemoved`). Other chapters keep their marks.
- **The edited dots now show in every stage, not only Editing.** Not yet edited is red; edited is **green in the Editing stage and orange in any other stage**. The right-click Mark Edited / Unmark Edited items were already there in every stage. Only the Editing stage still asks, when you leave a chapter, whether to mark it edited.
- **The red / green edited dots no longer disappear when the Studio's server has a bad moment.** The dots show only while the project's stage is an editing (review) stage, and the stage is fetched from the Studio. A failed fetch (the server erroring or out of CPU) was treated as "this project has no stages", which hid every dot until the next successful fetch. Now only a role that may not read workflows sees no stages; for any other failure Write keeps the stages it last had.

## Unreleased (an idle Cadrel no longer keeps the Studio's server busy)

- **Cause.** Two things made an app that was only left open ask the Studio's server for work, over and over. (1) Write checked every open file's lock **every 6 seconds**, and each check made the server list and permission-check the **whole vault**, once per open tab. (2) To answer that list the server checked each file against the permissions, and each check **read and parsed the project tree again**, so a vault of a few hundred files meant a few hundred database reads and JSON parses (the CPU limit) inside one request. The 3-minute background save also made a full pass even when nothing had changed anywhere.
- **The server reads the project tree once per request** instead of once per file. Listing the vault is one tree read however many files there are.
- **Lock checks no longer run on a timer.** A file's lock is looked at when it is opened, when the window gets focus, and again if a check-out or check-in is refused; the server decides who holds a lock, so a bar a little behind cannot cause harm. Several tabs asked at once share one request to the Studio.
- **The background save asks the Studio one tiny question first** (its change counter, two rows) and skips the full pass when nothing changed on the Studio or in the folder, so an idle app costs the server one small read every few minutes.
- **The phone and Reader ask the Studio whether anything changed before each minute's look**, and make a full pass (list the vault, people, projects, every file) only when it has. What you change on the phone still goes at once.
- Server code changed: use **Upgrade the server** for the CPU fix to take effect.

## 0.11.0 (People: invite anyone and give roles per project; a Read tab; invitation email)

- **The Studio's server can now invite a person without giving them a role** (server revision 6, database step 19). The invitation names the person (name and email); if someone with that email is already in the Studio's people it is that person, otherwise they are added. Whoever joins with it is that person and **can see nothing until the owner gives them a role on a project**. Invitations that name a role still work as before.

Invitations waiting can be given a **New link** or cancelled, and people who have joined can be removed. Below that are the people, teams and roles as before, and each person is marked *invited* or *joined*. A **Beta Reader** can only be given a project, so the whole-Studio choice is not offered for that role.
- **Moved:** the invitation controls and the member list in Admin → Studio Manager, and the *People and roles* card in Admin, are replaced by the People page. Studio Manager still builds, upgrades and links phones. Studio Managers no longer make invitations that name a role.
- **Each project has a *People on this project* card** (Projects page). It lists who has a role on the project: those given it here, those who have it from a project above (a Series' people appear on its Books, marked *from <Series>*; they are changed where they were given), and anyone with a role for the whole Studio, with each end date. **Add a person…** picks someone from the Studio's people and a role, with an optional end date; **Remove** takes away a role given on this project. Someone not in the list is invited from the People page (the card links there). Someone with no role on a project sees nothing of it.

This needs **Cloudflare Email Service** (a beta, on the Workers Paid plan) with a domain you have onboarded there (Cloudflare dashboard → Compute → Email Service → Email Sending → Onboard Domain) and an address on that domain. Turning it on uploads the Studio's server again with the email permission (and asks for your Cloudflare token unless it is kept); **Change address** and **Turn off** do the same; an upgrade keeps it. If Cloudflare says the address cannot send, nothing changes. Once it is on, the People page's **Create and email invitation** makes the invitation and emails it in one click, and a made invitation has **Send email to …** (from the Studio) as well as **Open in my mail app**. The server emails only an invitation that is waiting, and only to the address on that person's record (so it cannot be used to send anything else to anyone), and a failure is shown in Cloudflare's words with the link still there to copy. Without this, nothing changes: opening your own mail app still works, and a Studio that never turns it on is uploaded exactly as before.
- **A Read tab** (left rail, beside Write) is for a Studio you were **invited to**: it shows what that Studio's owner has opened to you as a Beta Reader, the same screen as Cadrel Reader. You joined the Studio once in Cadrel, and the same key reads there, so no second invitation is needed. It lists the manuscripts you have been given, in the chapters the owner has switched on, and opens one read-only with notes, as in Reader; they are kept under that Studio's *Shared With Me* folder. It appears only while the Studio in use is one you were invited to, and what it lists is whatever you hold *Beta Reader* on in that Studio. Joining a Studio is still done from the Studio menu on Home; there is no Open invitation button on this tab.
- **Cadrel Reader accepts an invitation with no role.** It says *nothing has been shared with you yet* without asking you to join again, and finds the manuscript once the owner gives you the project and switches chapters on. Invitations that name a role other than Beta Reader are still refused there, as before.
- A member who joined with a no-role invitation is shown with no role of their own in the Studio list.
- **Upgrading.** Each Studio's server needs **upgrading** (Admin → Studio Manager → Upgrade): this release is server revision 6 and database step 19. Until a Studio is upgraded the People page says so instead of offering invitations. Readers need **Cadrel Reader 0.12.0** to open an invitation that names no role. The app no longer makes invitations that name a role; ones already sent still work, and everyone already in a Studio keeps the access they have.

## 0.10.0 (Beta Readers join the Studio; the Studio's server no longer runs out of CPU; a fixed burn-down)

- **The Studio's server no longer runs out of CPU when a vault has many files.** Listing the vault (what a phone's first sync does), serving a file, and a Beta Reader's list of manuscripts checked each file's permission one at a time, and every check read and parsed the project tree from the database again and rebuilt the permission tables. A vault of a few hundred files made one request run hundreds of database queries (400 files: 404) and Cloudflare stopped it with *Exceeded CPU Time Limits*. The tree and the permissions are now read once per request and each decision is made once, so the same request is five queries however many files there are. **Upgrade each Studio's server** (Admin → Studio Manager): a Studio whose server was built before 0.8.1 still has the per-file code, and one built before this release has the part fixed here. The server revision is now 5, so the app offers the upgrade.
- **A Beta Reader is a Studio role.** Invite them like anyone else (Studio Manager → People); the invitation for a Beta Reader is a `cadrel-reader://join?…` link that opens Cadrel Reader. They have **no access until given a project**: a studio-wide grant of the role is refused, and an invitation that names no project gives them nothing.
- **Right-click the active manuscript → Manage Beta Read…** switches chapters on and off. A chapter that is off, and any chapter added later, is never sent: the Studio's server builds the text from the switched-on chapters only (`/v1/beta`), and a Beta Reader holds `beta.read` / `beta.comment`, not `manuscript.read`, so the vault, a file's versions and its contents are closed to them. Saved in the Studio (`beta_read`, `beta_note`; schema 18, server revision 4: press **Upgrade the server** once).
- **Cadrel Reader reads through the Studio.** *Open invitation…* takes the link, joins with a key made on the device (sealed by the operating system's store on Windows), and puts the manuscript under *Shared with me* as a project, in the chapters the author has on. It brings down new versions and changes to the chapters on every refresh, and says when access has been withdrawn. Their notes travel back to the Studio, and the author's Write takes every reader's notes into the project's Notes panel (one review file per reader). Readers cannot see each other's notes. Android Reader works the same way.
- **Google Drive review sharing is gone.** Removed: Write's **Notes → Share…** dialog and the Projects **Sharing** page, collaborator (edit) links, Google's file picker, the invitation page on GitHub Pages (and its workflow), and the Drive review code behind them. Cadrel Reader no longer opens Google Drive invitations (it says to ask for a Studio invitation), its home page and menu no longer mention Google Drive, and the phone apps no longer share. Google Drive *sync* of a person's own projects is separate and unchanged. People who edited a book with someone else through a Drive link: give them the Author role in the Studio instead.
- Tested against the real Studio server code (a chapter that is off never reaches the reader; the vault is closed to them; notes kept apart; new versions and later changes to the chapters reach them; withdrawn access is reported). Not yet tried on a real Studio.
- **The burn-down's steady-pace line is now fixed.** It runs from the words the manuscript had when the goal began, on the start date, to zero remaining on the deadline, and it moves **only if the start date, the deadline or the target word count changes**. Writing words, or the days passing, no longer shifts it, so *Words remaining* is measured against a line that means something. The **daily target** (the dashed horizontal line, *Needed per day*, the status-bar bar) is unchanged and is still recalculated each day from what is left and the days left.
- The starting point is kept in the goal (`startWords`), set when you save the goal. A goal made before this gets its starting point the first time its Progress window is opened, from the history as the line was drawn before. If the goal began before anything was recorded, the first recorded total stands in for the start.

## 0.9.1 (fixes: the assistant's edits of checked-in files, and a setting lost on closing)

- **The assistant (Claude) can no longer fail with a bare "EPERM: operation not permitted" when it edits a file.** Since 0.9.0 a file is read-only until it is checked out, and Windows will not rename a new copy over a read-only file, so an edit of a checked-in file ended in that error. The assistant's write tools now notice first and say what to do: *"… is read-only in Cadrel (it is checked in, or someone else has it checked out), so nothing was changed. The author needs to check it out first: open it in Cadrel Write and press Check out to edit, or use the Files page. Then ask again."* Nothing is written, kept aside or left behind when it refuses; once you have checked the file out it is edited as before, and you check it in to keep the change as a new version (or undo the check-out to throw it away). New files the assistant makes are unaffected.
- **Closing Cadrel now waits for what was just changed to be written to disk** (at most three seconds). Settings (the page you were on, colours, folders) and the Studio list are saved in the background, and the app could go before the last write finished on a slow disk, so a change made just before closing was sometimes not there at the next start. It showed up as a restart test that failed now and then on the build machines.

## 0.9.0 (check out, edit, check in; notes travel with the project)

- **A file is changed by checking it out, and only a check-in makes a version.** This replaces 0.8's "unsaved changes → Save version". A file is read-only until you check it out. **Write** shows the state above the editor: *Checked in · read-only* with **Check out to edit**; *Checked out by you* with **Check in…** (a comment, optional) and **Undo check-out**; or *Checked out by Ann* (read-only). The editor cannot be typed in until the file is checked out. The Files page has the same buttons. Nothing local is ever versioned: saving while a file is checked out writes the file, and the version is made at the check-in.
- **New files** in a project are added to the Studio and **stay checked out to you**, so you go on writing in them; their first check-in is their next version.
- **The phone works the same way.** The editor refuses until you check a file out, offers **Check out**, and **Check in…** (needs a connection; editing a file you have checked out needs none). A file checked out on the computer can be read on the phone, and changed once it is checked in there. The cloud button shows how many files are checked out on the phone, and its dialog lists them with **Check in**: save a version on one device before you carry on in the other.
- **Notes travel with the project.** A project's notes (`.cadrel/review/*.json`, where Write keeps them) are synced through the Studio on the computer and on the phone, merged by note (each by its id, the newer wins, replies united, deletions kept), so notes made on either end up on both. They are not checked out and not listed as files; they are saved at most every couple of minutes so a flurry of notes is one version, not twenty.
- **An administrator can release a lock, in Write too.** When someone else (or your own lost phone) has a file checked out, an administrator (the `vault.force` capability) sees **Release…** in Write's bar as well as on the Files page: it asks why, takes the lock, and is recorded. What the holder had not checked in is kept aside on their device, never deleted; what was checked in is safe. Nobody else is offered the button.
- **Changes made without a check-out** (from 0.8, or a program that ignores read-only) are left exactly as they are, never versioned and never overwritten, and listed: **Check out, keeping my changes** takes the file as it is (refused if a newer version exists, so nothing is lost).
- Files made read-only by this are made so on the first pass after upgrading; nothing is deleted.
- Not changed: the Studio's server, so there is nothing to upgrade there.
- Tested with the real vault and server code (desktop, phone, notes merge, offline, held by the other device) and the bar's states; not yet on a real Studio and phone.

## 0.8.1 (fix: the phone could not sync a large vault)

- **The Studio's server no longer checks the whole vault for every file it serves.** Downloading one file's contents made the server list and permission-check every file in the Studio first, and so did every call that named a file (check-out, check-in, versions, references). With the hundreds of files that 0.8.0's automatic saving puts in the vault, the phone's first sync (it downloads each file) asked for hundreds of these and the Studio answered "status 503". Now each call looks only at the file it is about, and contents are checked against the files that hold them, in batches. Same rules about who may read what; covered by tests, including 60 files holding the same contents.
- Raises the Studio server revision to 2, so Studio Manager offers **Upgrade the server**: press it once after installing (the fix is in the server's code, not only in the apps).

## 0.8.0 (one folder: your projects are the vault)

- **The Projects folder is the vault.** The vault used to have a folder of its own (`<Studio>\Vault`) beside Projects, so a manuscript had to be copied there and added by hand, and the phone saw nothing until it was. Now there is one folder. New files in a project are saved to the Studio automatically, versions made elsewhere (another computer, the phone) come in, and files other people or the phone create appear. You never add a file to the vault.
- **Versions are only ever made by you.** What you change stays in your folder, listed on the Files page as *Changed, not saved as a version*, and is never overwritten. A version is made when you press **Save version** (or check a file in), so history holds what you chose to keep and does not grow with every Save in Write. *Check out* stays for when you want a file to yourself for a while. Files are no longer read-only.
- **Nothing is lost.** If a version is saved over a newer one made elsewhere, both are kept: the newer one is in place and yours sits beside it as `Name (changes <date> <computer>).md`. A file someone checked out on purpose waits and says so.
- **How it works:** a quick look at the folder every 15 seconds (sizes and times only, no network) and a full pass when something changed, when the window gets focus, and every 3 minutes (so the Studio's server is not read more than before). On quit, new files are saved first. Cadrel's own folders (`.cadrel`), `Exports`, `Trash`, temporary files and anything loose in the Projects folder outside a project are never saved. Files over 95 MB are listed and left alone.
- **Moving over.** The first run copies what the old `Vault\` folder held into the Projects folder, never overwriting; a file that differs stays in the old folder and is listed as your unsaved change. The old folder is left in place. What the vault knows about each copy now lives in the Studio's own folder, not in Projects.
- **Files page:** says all this, shows how syncing is going, has **Sync now** and **Save version…**. The phone's list is unchanged: it already read the vault, so your projects now appear on it.
- **The phone works the same way.** It used to save a version each time it synced a file you edited there. Now an edit stays on the phone, listed under *Changes not saved as a version yet* (the cloud button shows how many), and is never overwritten by a newer version; **Save version** there makes one version. If the file moved on meanwhile, or someone holds it, both are kept. Hand-off between your devices is: save a version on one, then carry on in the other.
- Tested with the real vault on a records file (new, edited several times, newer-elsewhere, both-changed, held, moved-over); not yet with a real Studio server and a phone.

## 0.7.0 (M2: the team vault and M3: Editorial, in development)

- **Editorial passes.** A developmental, line, copy or proof edit of one manuscript is now a record: it covers an exact version of the file (and of an edit brief), has an editor, and moves planned, in progress, delivered, responded, closed. The Editor raises **queries, comments and suggestions** anchored to passages of that version; the Author answers every query and accepts, rejects or defers every suggestion (a reason is required to reject or defer, a date to defer); each decision is written to the decision ledger, and a deferral makes a task for the revisit. A pass cannot be marked responded while a query is unanswered or a suggestion undecided. Briefs (for the manuscript and for an edit) are written on the book's page and keep every version. The Editing page, in the rail after Planner, plans passes, reads the exact text of the version, raises items from selected text, compares the covered version with a later one side by side, and checks which accepted changes were made, changed or missed.
- **Gates.** A workflow move can require a closed developmental, line or copy edit and every query answered. A proofread only advises: a gate cannot ask for one.
- **The Author can answer with no connection.** On a Studio whose records are on its server, what was last read is kept on the computer, and answers and decisions are checked, kept, shown as made, and sent in order when the Studio is back; one the server turns down is kept aside with its reason and the Author's own words.
- **The assistant** has four editorial tools (`edit_passes`, `edit_items`, `edit_read`, `edit_raise`) for a Studio whose records are on this computer. It can raise items as the Editor but never answer, decide, move a pass along or close it.
- **Rewrite mode in Write (desktop only).** Right-click a manuscript: a new file is made beside it (from a copy or a blank page) and linked; the two show side by side, the original read only, scrolling together paragraph by paragraph. Either file turns it on or off, or unlinks.
- **Export fonts.** Chapter headings and body text have separate fonts in the EPUB and print PDF settings, and twelve more SIL OFL fonts are included (Literata, Source Serif 4, Alegreya, Spectral, Merriweather, Lora, Gelasio, Cormorant Garamond, Playfair Display, Marcellus, Fraunces, Bodoni Moda). Every font keeps its own copyright notice and licence, which also go into each EPUB that embeds it; a family whose licence names a Reserved Font Name is shipped unmodified.
- **Pages ask again when you move to them**, so a note or project made in Write or Market is there when you open Notes or Projects (the pages otherwise refresh on focus, after your own change, and every three minutes).
- Studio schema version 16 (migrations 0012 to 0016). An app from before this version will not open an upgraded Studio. Tested against a stand-in for Cloudflare that runs the real Worker code, not against a Cloudflare account.
- **A Studio's database is read far less.** A Studio's D1 database (Cloudflare bills every row it reads) was read about 6.7 million times in a day by a small Studio, nearly all of it from the same few queries: every permission check re-read every role, capability, assignment, person and team, up to three times over, on every call, and the app refreshed its pages every 10 to 15 seconds. Now the Worker keeps who holds what until it changes; the Studio keeps two change counters (`data_version`, `access_version`, in `studio_meta`, moved in the same batch as the change that caused them) and answers `GET /v1/version` (two rows); the app keeps the answers to its reads and asks the counter, at most every 3 seconds, instead of asking for them again, and its minute-by-minute project sync fetches the tree only when the counter moved; old request signatures are swept once a minute, not on every request; pages and the project sync ask when they open, when the window gets focus and after your own change, and otherwise only every three minutes while the window is open and visible (it was every 10 to 15 seconds, and every minute), and not at all while it is hidden or minimized; and the health check no longer counts a table. A change is seen at once by the person who made it and within a few seconds by everyone else. No new schema version, so no older app is locked out, and an app talking to a Studio that has no counters yet simply asks every time as before.
- **One AI connection for every Studio, following switches live.** The Claude Desktop extension (and the AI Kit and by-hand snippets) used to have the Studio that was active when it was downloaded written into it, so after switching Studio the assistant went on reading the old Studio's projects, and reinstalling was the only cure. They now say only `--active <file>`; Cadrel keeps that file as the active Studio's server arguments, and the extension's launcher restarts the server on the new Studio when the file changes, without reconnecting. Install the extension once more (Assistants → Download the Claude Desktop extension) to get this; after that it never needs reinstalling. See docs/STUDIOS.md.
- **A Studio's records and vault can live on its server, for everyone.** Until now a built Studio's server knew only who was in it; a joined Studio showed "managed by its owner" and each computer had its own copy of everything. Now the server holds the records (people, roles, teams, catalogue, tasks, sign-offs, decisions, business records) and the vault, and **every permission check is made on the server**, by the same code the app ran in-process. A Studio you join is always used this way; a Studio you own is moved once with **Admin → Studio Manager → Move this Studio's records to its server** (records, vault file contents and projects; your file is kept as a copy; it can be run again). The server answers the service's calls as the person whose key signed the request, from a list of names (nothing else is reachable), and a refusal comes back as the same kind of error as before. An invitation can now say **which project the role applies to and for how many days**: a freelance guest is given one book for a while, sees that book's files and nothing else, and the grant lapses on its date. Tested against the real Worker code with SQLite behind D1 and a map behind R2, not against Cloudflare itself.
- **The vault on the server: check-out locking, versions, force release.** Check-out is one row the database keeps unique, so two people cannot both hold a file; only the holder, on that machine, checks in; a version's contents must be in the Studio's R2 store first and are kept there by their SHA-256 (also a copy on each computer, so a version is fetched once); an administrator with `vault.force` removes a lock with a reason and **the holder's unsaved work is kept next to the file on their computer** the next time they connect, never lost; a late check-in is refused. A file is a manuscript or an asset and is governed by `manuscript.*` or `asset.*` on the project its data card names. References, where-used and data cards work through the server too. Files over 95 MB are refused (the Worker's request limit). The exit test (author checks a chapter out, editor sees the lock, author checks in, editor gets the new version; an administrator force-releases and the holder's work is kept; a guest sees one book) is a test that runs with real files in two working folders against the Worker.
- **Offline.** If the Studio cannot be reached, the Files page shows what it last knew and says so, files you have checked out can still be edited, and check-in, check-out and Get latest wait for the connection; a Studio that could not be reached at start is tried again every minute.
- **The owner's projects reach everyone.** The owner's project tree is published whenever it changes; others receive their own part of it (a role on one book shows that book and the series above as a container) and cannot change it from their computer (a sentence says why). Members moving a project between stages is not possible yet.
- **Shared Market captures.** *Settings → Captures shared with this Studio* sends the captures (pages and covers) the Studio lacks and fetches the ones this computer lacks, reading them in with Market's own import, which keeps what is already there. Append-only, and needs `market.capture` to send and `market.read` to fetch.
- **Back up and put back the server's records.** *Back up the server's records* writes every record, who the owner is and the projects to one file; *Put back from a backup…* replaces the server's records with it (not allowed from a newer Cadrel). File contents are not in it; they stay in the file store. The Studio's schema is now 11 (`0011_server.sql`: an invitation's project and end date); an older Cadrel is refused a Studio that is ahead of it, and a Studio is never taken backwards.
- **Roles that may not see a page get an answer, not an error.** The people and roles page, project work, planning, Home and the Dashboard say what the role does not allow instead of failing; everyone in the Studio sees names (not emails or roles) wherever a task, sign-off or lock belongs to someone.
- **What is not done in M2.** A code-signed installer (the workflow signs when it is given a certificate; there is none yet), updates from the Studio's server, replicating the file store, the security policy page, separate Author / Editor / Director dashboards, the assistant's record tools for a Studio whose records are on the server, live updates and notifications, and any run against a real Cloudflare account. See docs/STUDIOS.md.

## 0.7.2 (Android apps, and the assistant reaches more of a series)

- **A manuscript kept in a series' own folder can be reached.** A Project with one open Book sent every book-level call to that Book, so a first book whose manuscript sits in the series folder (not a Book of its own) could not be read or given notes. - **Fixed: backing up and restoring a Studio lost or broke its records.** A review of the backup code found three problems, all in whole-Studio backups (a backup of one project was fine).
