# Changelog

Versions are `MAJOR.MINOR.FIX`; see [docs/VERSIONING.md](docs/VERSIONING.md). Newest first.

## Unreleased (M1)

- **Planner: the pipeline and the calendar** (rail, below Dashboard). **Pipeline**: every live project and subproject as a card in a column per stage of its workflow (pick the workflow; show projects, subprojects or both), with its kind, the project above it, open tasks, how many are late and when the next date is; a card opens the project. **Calendar**: a Monday-first month grid of every task and deadline (deadlines in bold, finished work struck through, late work marked), previous/next month and Today, a filter for everyone's or only yours, a "Late" list and a "No date" list beside it; an item opens its project. Archived projects and cancelled work are left out. It reads the same records the Projects page edits, so nothing is entered twice. Not built: dragging a card to move its stage (a move still goes through its gates on the project's page), dragging a task to a new date, week and day views, and sharing the calendar as a feed.

- **Tasks, deadlines, approvals and decisions** (migration `0007_work.sql`, Studio schema 7). They belong to projects and subprojects. **Tasks and deadlines**: a title, notes, an assignee, a due date; a deadline is a task that must have a date; a task can wait for others in the same project (never in a loop), and cannot be marked done while what it waits for is open; cancelled and finished tasks stay on the record. **Approvals** are sign-offs under a label ("Cover approved") that the named people give: you say who is asked and how many must agree, any one rejection (with a reason) closes it as rejected, only a person it names can answer it (not even an Owner can answer for someone else), one request per label can be pending at a time, and a project stands approved under a label while its latest decided request was approved (a later rejection takes it away). **Decisions** are an append-only ledger (title, context, outcome, who and when); nothing edits or removes an entry, a later one can replace an earlier one once and the earlier stays on the record. **Gates can now ask for them**: two new conditions in the workflow builder, "no open tasks" (the project and its subprojects) and "signed off" (one gate can require several labels), with the reason shown on the move when it is closed. Permissions: reading needs `task.read`; making or changing your own tasks, asking for a sign-off and recording a decision need `task.edit`; giving work to someone else needs `task.assign`; changing anyone's task or withdrawing someone else's request needs `task.manage` (tested for all twelve default roles). In the app: each project's page has Tasks and deadlines, Sign-offs (ask, approve, reject, withdraw) and Decisions (record, replace) for the project and its subprojects, and Home shows "Waiting on you" (sign-offs asked of you and your open tasks, late ones marked). Not built: reminders and notifications, task templates, a calendar view, recurring tasks, approvals of a specific file version (they arrive with the vault), and transition actions such as "create tasks from a template when a project moves".

- **Stages belong to projects and subprojects, and Write uses Cadrel's.** Write no longer has statuses of its own: the project's stage comes from Cadrel's workflow, is shown read-only in Write (project list, switcher, quick switcher, settings), is never written to `project.json`, and a stage of kind "review" (Editing in the default) turns on Write's edited-chapter marking. **Several workflows can exist, and each level has its own default** (Admin → Workflows: "Default for new projects" / "Default for new subprojects"), so a series can use a different workflow from its books, and any two projects can differ. **The workflow is chosen when a project or subproject is created (New project dialog) and cannot be changed afterwards**; the stage moves only through a move the workflow has, with its gate open (roles, and conditions on the project: a manuscript is linked, no open notes under it, it has subprojects, its subprojects are all done), shown on the project's page with the reason for any move that is closed. Dropping a stage in the builder asks where its projects go; a workflow in use, or a default, cannot be deleted. Projects made earlier get their level's default once, starting in the status they had. A workflow's stages stay what they were: **the default is MDEdit's own list, Planning, Drafting, Revising, Editing, Published, On hold, with every move open**. Removed from books: stage and workflow (the catalogue keeps books; stages are on projects). Migration `0006_workflow_levels.sql` (Studio schema 6).

- **Workflow builder** (Admin → Workflows): add, rename, recolour, reorder and remove stages, tick the moves, set a gate per move (roles allowed, conditions), copy a workflow, create a blank one, set the default per level; shows how many projects use each workflow. The page can only ask for a fixed list of changes.

- **People and roles in Admin** (the role editor). Admin → People and roles has three tabs. **People**: add people (employee, contractor or guest, optional email), edit them, deactivate and reactivate, see and give roles (a role for the whole studio or for one project, with an optional end date), team membership, pen names (add one, or share an existing one), and **Explain access**: pick an action and the studio or a book and see exactly which assignment allows or blocks it. **Teams**: create, rename, delete, members, roles given to the team. **Roles**: the twelve defaults plus your own; a capability checklist grouped by area with plain-language descriptions, Copy, Reset to default, Delete (moving its people to another role), and who holds each role; the Owner role is shown but cannot be changed, and the last Owner has no Remove or Deactivate. A "new capabilities to review" notice appears when a newer version adds a power no role has yet. A Studio you own keeps its records in `records.db` in its data folder and starts with the default roles and you as Owner; every change goes through the permission-checked service as you, so a refusal (for example giving away a power you do not hold) comes back with its reason. A Studio you only joined shows that its people are managed by its owner until the server side (M2). The page can only ask for a fixed list of changes (a test pins it, including that `constructor` and `__proto__` are not among them).

- **People, teams, roles and assignments** (records, service and guardrails; the screen is next). Migration `0004_people_roles.sql` (Studio schema 4). `@cadrel/kernel` `people.ts`: people with a kind and unique email (deactivate, never delete: their assignments and team membership stop applying and come back on reactivation), pen names shared between people, teams, roles (create, copy, edit capabilities, reset a default to the shipped matrix, delete with a replacement role that the people are moved to), assignments (person or team × role × scope × expiry, once), a capability review for powers a newer version adds, `loadAccess` (what `can` reads) and `bootstrapStudio` (twelve default roles and the first person as Owner, safe to run on every start). The Owner role holds every capability, including future ones. `@cadrel/service` `people`: every operation checked with `can` and the guardrails: you cannot hand out a governance power you do not hold, nobody grants themselves a role, only an Owner gives, changes or removes Owners, and the last Owner cannot be removed, expired or deactivated; Explain access and effective capabilities for the role editor; `dbAccess` reads who holds what from the records on every call, so a change applies at once. Tests include the role matrix against each operation, and a randomized run of hundreds of role-manager actions that checks nobody ends up with a governance power the role manager lacked.

- **Shared records, first part: the catalogue, the store and the service** (no screens yet). `@cadrel/kernel` gains `catalogue` (IP, series, books at positions, editions with ASIN and ISBN, checked ISBN-10/13, UUIDv7 ids) and its migration `0003_catalogue.sql` (Studio schema 3; an app that knows 2 is told to update). Names, positions, ASINs and ISBNs are unique in the database itself, so two writers cannot both succeed; a book is found from an ASIN with `bookByAsin`, which is the join to Market and Finance. `@cadrel/store` opens the Studio's records as a SQLite file with the Worker's own migrations (and refuses a newer file). `@cadrel/service` runs every catalogue call through `can` for a named person; the one-person Studio runs as its Owner. Also fixed: the permissions doc's royalties row had gained words the role-matrix test compares exactly, which failed `kernel`'s test; the note moved under the table.

- **Payment calculators and roll-ups, per book.** Finance's book page has **Payments** (every KDP payment the book is in: the whole payment beside the book's part of it before tax, tax and after tax, allocation status, and what the book has earned that no payment covers yet) with the payment calculator limited to the book (authors, expandable to lines; Save CSV, or PDF for one author or one per author), and **Payments by period** (month, quarter, year or custom: what the book's payments owe each author, saved as CSV or a PDF per author). The book's parts always add up to the whole payment to the cent (tested). Allocating (freezing) stays a whole-payment action on the Payments tab; the book view only shows it. Payouts, carried-in and "due" are per author across all their books, so the one-book roll-up has none of them and points to Pay authors. My Books' book page lists the same payments, and **Save** now includes them: the book's payment calculators and roll-up (CSV and PDF) in a Payments folder, and author statements that are the book's own lines only (named with the ASIN). In the library: `royaltyStatement`, `paymentOwed`, `payoutRollup` and the statement/payment/roll-up files take an optional ASIN; new `bookPayments`.

- **Per-book pages in Finance and My Books, and Open on Amazon everywhere.** Finance: open any book from the Reports tab (or "Open in Finance" in My Books) for its own page: royalties, units and pages with the share that rests on estimates, a chart and table by month (reported or estimated), by marketplace, royalty rate and kind of sale, its split, **Open on Amazon**, **Save earnings (CSV)…** and a last-12-months / all-months switch. It is Finance's analysis limited to the book (`moneyAnalysis(from, to, asin)`), so it always agrees with the Charts tab. My Books: **Open on Amazon** (the same Amazon-only opener Market uses) beside Open in Market and Open in Finance; Finance's button is absent for roles without royalties. Market's book page already had Open on Amazon, for captured and uncaptured books alike. The earnings spreadsheet is made in one place (`bookEarningsFile`) for both Finance and My Books, now with eBook / print / Kindle+ columns.

- **My Books** (rail: below Home). One page per published book, assembled from Market and Finance with no data of its own: listing and rank/price history, category lists, sales and royalties by month (reported or estimated, never mixed), splits, the book's notes, and a Save bar ("Save everything for this book", Market exports, earnings and author statements as CSV and PDF) that uses the same generators as Market's and Finance's own Save buttons and writes into a new folder each time. Finance's sections are left out (not shown as zero) for roles without royalties, decided in the main process; Authors see none until agreements exist. Opens the book in Market's Library, and Finance. 11 tests.

- **Finance is its own module** (rail: after Market; `packages/finance-desktop`). KDP report import, charts and analysis, the Month view, royalties and splits, payments, paying authors and the sales-estimate calibration moved out of Market's Library → My Books and Settings into Finance, with the same behaviour and the same data (still in Market's library). Market keeps research and its list of your own books; its book page and list no longer show sales. Finance has its own bridge (`window.cadrelFinance`, `finance:*` channels, callable only by the Finance view). Export-save dialogs for statements, calculators and roll-ups moved with it; tests use `CADREL_FINANCE_TEST_EXPORT_DIR` and `CADREL_FINANCE_TEST_FOLDER` in place of the Market variables.

- **Backup and import** (Settings → Backup and import; `packages/shell/src/main/backup.ts`). **Back up this Studio…** writes one `.cadrel-backup` file (a zip with a manifest of every file's size and SHA-256) holding the Studio's data folder and its project folders; keys, tokens and `secrets` are never included, and caches and logs are left out. The file is read back and every checksum checked before it is moved into place, and an existing file is never overwritten. **Open a backup…** checks one and lists its projects; **Restore into this Studio** puts a project beside the others under a free name, and **Restore everything as a new Studio** makes a new Studio from the whole backup. Nothing is ever restored over existing files; a backup from a newer Cadrel is refused with "update Cadrel". **Import from MDEdit** takes a project folder or a Root Folder, shows what it found and what is not carried over (Google Drive sync state and backup copies), then copies the project as a Cadrel project with its status, goals, active manuscript, edited marks, review notes and settings; the original is untouched and importing the same project again is recognised. Replaces the disabled Backup button in the Studio Manager. 14 tests; the Electron end-to-end run for the new page is not done yet.

## 0.2.0

- **Data packs made by BookScout import again.** The rename to Cadrel Market changed the tag inside a pack (`bookscout-data-pack` to `cadrel-market-data-pack`), so every older pack was refused as "not a Cadrel Market data pack". Both tags are accepted now; the layout is the same.
- **The Cadrel window has real rounded corners on Windows, and its own window buttons.** Windows draws a square grey outline around a frameless window and rounds nothing, so the rounded shell sat inside a square frame. The window is now transparent and frameless: the shell draws the rounded outline, Write's and Market's views are rounded to match, and minimise / maximise / close are drawn by Cadrel in a small view above everything, in the border's colour with a rounded top-right corner (and rounded where they meet the page's card). Maximised and full-screen windows are square, as they should be. Not yet checked on a real Windows machine: please check that the edges still resize.
- **Port 47321 taken: Market now says by whom, and can quit it.** When the capture server cannot start because the port is busy, the message names the program holding it (for example `BookScout.exe (process 1234)`, found with `netstat`/`tasklist` on Windows and `lsof` elsewhere), and Settings and the Dashboard offer **Quit <program> and reconnect** (asks first; looks the holder up again at that moment and never quits Cadrel itself). The Market header shows **Fix…** while it is not listening. Quitting Cadrel Market or the Cadrel shell now closes the capture server and waits for it before the process exits (3 s at most), so the port is released cleanly; closing a window with "keep running in the tray" on still leaves it listening, as before — and Settings now says so.
- **Market's capture server handles a busy port 47321 better.** A bind failure is retried a few times before giving up, since it is often just the previous process (an old BookScout/Cadrel Market build, or this app's own tray icon) still releasing the socket. When it really is held, the message now says, where it can tell, whether another copy of Cadrel Market is the one holding it. **Reconnect** no longer closes and reopens the library on every try, and a new **Force disconnect** stops the capture server on demand (library untouched) so the port is free immediately — both are on Settings in the standalone app and on the Dashboard's Market card in the shell.
- **M0: one app.** MDEdit 0.8.5 and BookScout 0.6.3 are imported (`@cadrel/write`, `@cadrel/market-*`) and run together in a new shell (`@cadrel/shell`): left rail, Home, Dashboard, Write and Market in their own views. Electron 44 and a single pdf.js across the workspace. Windows installer, packaged-app smoke test and CI to build and publish them.

- **Names, from the start:** the apps are Cadrel Write and Cadrel Market everywhere, including on disk (`%APPDATA%\Cadrel\write` and `\market`, `.cadrel` project folders, `window.cadrelWrite` / `window.cadrelMarket`, `CADREL_*` variables, `cadrel-*` skills). No migration from the old names is built. The default projects folder is `<home>\Cadrel`.
- **The assistant can read the user's attached files** (`studio_user_file`), with a switch on each file (no global opt-out), and a log of what it opened.
- **The Cadrel folder.** Each Studio's work lives in `<home>\Cadrel\<Studio>\` (wherever the user's home is, another drive included) as `Projects`, `Write` and `Market`; nothing to set up. Settings → Where things are kept moves the Cadrel folder (at the next start, with every Studio's folder) or places the active Studio's Projects, Write or Market elsewhere (Change… / Use the default).
- **Admin page** (above Profile, shown only to the studio's owner and administrators): the project templates are central to Cadrel and edited here, with Write's own editor reused. Only Projects uses them; Write has no templates tab or New Project. Changes are checked on the main-process side (`AdminStore.save` refuses a member). Roles come from the server once there is one; until then a one-person studio's person is its Owner.
- **Studios, for real** (see `docs/STUDIOS.md`). Each Studio is independent and walled off: its own data folder (`studios/<id>`), its own working folders (`<Cadrel>/<Studio>/{Projects,Write,Market}`), profile, templates, database and file store. Choosing another Studio on Home restarts Cadrel into it, so two Studios' data are never open together, and the AI server is pinned to the active Studio. The Cadrel folder moves at the next start (nothing may be open while it moves).
- **Studio Manager** (Admin, off until enabled): **Provision** builds a Studio in the owner's own Cloudflare account through Cloudflare's API (D1 database, R2 bucket, the Studio server Worker bundled in the app), safe to repeat; **Keep this token** stores the Cloudflare token encrypted for upgrades, with **Forget it**; **Upgrade the server** (never backwards); **invitations** by role as links that work once, **Join a Studio** on Home, members and pending invitations listed with Remove / Cancel. People are keys, not passwords: Ed25519 signatures, and the invitee checks the owner's fingerprint before sending anything. Backup: see Unreleased.
- **One Studio for every build.** Development builds and releases use the same Studio instance and registry; the release workflow no longer deploys a Worker, and the Worker's schema is only added to.
- **AI Assistants page:** the AI Kit, the Claude Desktop extension, the by-hand settings for Claude Code / Claude Desktop / Codex and the online door for ChatGPT moved here from Write's AI dialog and Market's settings. The assistant reads manuscripts from the Projects folder.
- **Updates:** Settings → Updates checks GitHub, notes a new version (with its release notes and a dot on Settings in the rail) and installs it on Windows after verifying it. A development build (`-dev.N`) is offered development releases only and a stable build stable ones.
- **Projects page owns the project folders.** Creating (with a manuscript-folder template), renaming, duplicating, archiving, deleting, status, and adopting unfiled folders happen on Projects (`ProjectManager` in the shell). Write lists and opens projects, with no create/rename/delete/archive/convert, no welcome dialog and no Root Folder setting (capability `manageProjects`, true only on the phone). Write's Settings keep the project *templates*, and per-book settings (goals, defaults) stay in Write.
- **Profile:** the photo is a click away and kept with the user's files; attached files can be downloaded. Left rail order: Home, Dashboard, Projects, Notes, Write, Market.
- **The user** (`window.cadrel.user`): a profile (name, email, pen names, about me, photo) and files attached to it, at the shell level, with a Profile page and the photo in the rail. The name replaces the old "name on notes" setting. The assistant can read name, pen names and about-me, never email or files.
- **Export acts on one chosen file only**: from the open file or by right-click on any file. No marking step, no automatic pick, no file picker in the dialog.
- **File kinds** (`@cadrel/kernel`): the built-in kind registry, including `image`, with suggestions from folder and extension. Design in `docs/FILES.md`; not yet wired into the catalog.
- **Projects with subprojects** are the structure everything hangs from (`@cadrel/kernel`, `@cadrel/studio`, the Projects page): a Series is a project and each Book a subproject by convention, not by rule. Manuscripts and market categories are linked to a project; words, goals and open notes roll up from its subtree; permission scopes follow the tree. The AI server gains `studio_*` tools (it can organise projects but not delete them).
- **Notes across modules**: MDEdit's Notes generalised to any record in any module, one shared panel, one studio-wide Notes page that also lists the review notes inside manuscripts.
- **The shell as global controller**: one appearance setting (light/dark and colours) for Home, Write and Market, the name on notes, folders overview; Write's own Appearance settings point to Cadrel's.
- **Cadrel look**: the supplied emblem as the app, installer and rail icon; slate-and-stone palette on MDEdit's design language.
- **One assistant connection.** A single MCP server (`@cadrel/mcp`, name `cadrel`) carries all of Write's tools, resources and editing prompts plus Market's tools. Write's AI Kit and Market's Claude connection both produce the same one `cadrel` Claude Desktop extension. `search_book_text` is Market's former `search_text` (Write keeps `search_text`). The HTTP door serves Write only unless started with `--with-market`.
- Kernel (`@cadrel/kernel`): capability catalogue, the twelve default roles (tested cell for cell against `docs/PERMISSIONS.md`), the permission engine (`can` / `explain`, scopes, teams, expiry, confidential projects, workflow-state denial), role guardrails, and the vault check-out / check-in / undo / force-release logic.
- Studio server (`@cadrel/worker`) skeleton on Cloudflare with D1 and R2 (`cadrel-dev-*` for dev, `cadrel-*` for production), vault migration, and a health endpoint; deployed from the release workflow.
- Plan: PDM-style vault, Cloudflare, shared captures, Windows only, roles and permissions design.
