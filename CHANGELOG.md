# Changelog

Versions are `MAJOR.MINOR.FIX`; see [docs/VERSIONING.md](docs/VERSIONING.md). Newest first.

## 0.7.0 (M2: the team vault, in development)

- **A Studio's records and vault can live on its server, for everyone.** Until now a built Studio's server knew only who was in it; a joined Studio showed "managed by its owner" and each computer had its own copy of everything. Now the server holds the records (people, roles, teams, catalogue, tasks, sign-offs, decisions, business records) and the vault, and **every permission check is made on the server**, by the same code the app ran in-process. A Studio you join is always used this way; a Studio you own is moved once with **Admin → Studio Manager → Move this Studio's records to its server** (records, vault file contents and projects; your file is kept as a copy; it can be run again). The server answers the service's calls as the person whose key signed the request, from a list of names (nothing else is reachable), and a refusal comes back as the same kind of error as before. An invitation can now say **which project the role applies to and for how many days**: a freelance guest is given one book for a while, sees that book's files and nothing else, and the grant lapses on its date. Tested against the real Worker code with SQLite behind D1 and a map behind R2, not against Cloudflare itself.
- **The vault on the server: check-out locking, versions, force release.** Check-out is one row the database keeps unique, so two people cannot both hold a file; only the holder, on that machine, checks in; a version's contents must be in the Studio's R2 store first and are kept there by their SHA-256 (also a copy on each computer, so a version is fetched once); an administrator with `vault.force` removes a lock with a reason and **the holder's unsaved work is kept next to the file on their computer** the next time they connect, never lost; a late check-in is refused. A file is a manuscript or an asset and is governed by `manuscript.*` or `asset.*` on the project its data card names. References, where-used and data cards work through the server too. Files over 95 MB are refused (the Worker's request limit). The exit test (author checks a chapter out, editor sees the lock, author checks in, editor gets the new version; an administrator force-releases and the holder's work is kept; a guest sees one book) is a test that runs with real files in two working folders against the Worker.
- **Offline.** If the Studio cannot be reached, the Files page shows what it last knew and says so, files you have checked out can still be edited, and check-in, check-out and Get latest wait for the connection; a Studio that could not be reached at start is tried again every minute.
- **The owner's projects reach everyone.** The owner's project tree is published whenever it changes; others receive their own part of it (a role on one book shows that book and the series above as a container) and cannot change it from their computer (a sentence says why). Members moving a project between stages is not possible yet.
- **Shared Market captures.** *Settings → Captures shared with this Studio* sends the captures (pages and covers) the Studio lacks and fetches the ones this computer lacks, reading them in with Market's own import, which keeps what is already there. Append-only, and needs `market.capture` to send and `market.read` to fetch.
- **Back up and put back the server's records.** *Back up the server's records* writes every record, who the owner is and the projects to one file; *Put back from a backup…* replaces the server's records with it (not allowed from a newer Cadrel). File contents are not in it; they stay in the file store. The Studio's schema is now 11 (`0011_server.sql`: an invitation's project and end date); an older Cadrel is refused a Studio that is ahead of it, and a Studio is never taken backwards.
- **Roles that may not see a page get an answer, not an error.** The people and roles page, project work, planning, Home and the Dashboard say what the role does not allow instead of failing; everyone in the Studio sees names (not emails or roles) wherever a task, sign-off or lock belongs to someone.
- **A server built before this is told to upgrade, not half-opened.** A Studio you joined whose server has not been upgraded yet shows a sentence saying its owner must use *Upgrade the server*, and the owner cannot move records to a server that has not been upgraded. (Upgrading is in the Studio Manager and needs the Cloudflare token.)
- **What is not done in M2.** A code-signed installer (the workflow signs when it is given a certificate; there is none yet), updates from the Studio's server, replicating the file store, the security policy page, separate Author / Editor / Director dashboards, the assistant's record tools for a Studio whose records are on the server, live updates and notifications, and any run against a real Cloudflare account. See docs/STUDIOS.md.

## Cadrel Reader 0.9.0

Cadrel Reader is a new, separate app for beta readers (released under tags `reader-vX.Y.Z`; its version is in `packages/reader/VERSION`). It is Write's reading and review experience on its own: open an invitation, read the manuscript, leave comments and suggestions, and they reach the author through Google Drive. It has no writing, sharing, export, import, AI or project management. It has its own installer (`CadrelReader-Setup-<version>.exe`), its own data folder (`%APPDATA%\Cadrel Reader`, shared projects in `Documents\Cadrel Reader\Shared With Me`) and its own update feed, and it installs beside Cadrel. See [packages/reader/README.md](packages/reader/README.md).

## 0.6.1

- **The assistant can give a project its manuscript folder.** A project made through the assistant had no folder, so none of the writing tools could work on it. `studio_add_folder` makes the folder from a template (Novel, Series, Short Story or Blank) inside the Projects folder, whole or not at all, and links it to the project or book; the writing tools then make the subfolders and files they need.
- **The assistant can link more to a project or book.** Beyond manuscripts, Market categories, comparable titles and people, `books_link_project` links a catalogue book to the project it is made in (or unlinks it). All of the linking tools work on a book or a subproject as well as on a project.
- **Market captures can be brought across Studios.** Each Studio keeps its own Market library, so captures made while another Studio was open were not in the one you were using. **Settings → Market captures from another Studio** copies them across: pages already in the library are kept and the other library is not changed. (Two Studios can still share one library by choosing the same Market folder for both.)

## 0.6.0

- **The assistant can manage projects.** Beyond organising them, it can now create a series, a book (which starts in the first stage of the default workflow for new books) or a standalone novel made whole; reorder a project among its siblings; link a comparable title by ASIN as well as manuscripts and Market categories; show a Book's stage and move, close or reopen it through the same gates the Projects page uses (every reason comes back when a move is not open); and see and change who is assigned to a project (`studio_people`, `studio_roles`, `studio_assign`, `studio_unassign`), under the permissions of the person it acts for. It still cannot delete a project, and it cannot approve a sign-off.
- **Tasks, sign-offs and decisions follow who is assigned to the project.** People see and work on the records of the projects they are assigned to, and no others. A task or a sign-off can be given only to someone assigned to its project (a role on the project, or the series above it; the Owner and Admin always qualify), and the pickers on the project page list only those people, with a note when nobody is assigned yet. A role given on one project now lets someone work on that project's records, where before a role had to be studio-wide to count. The assistant's `work_people` takes a `project` to list who can be given work there. See docs/PERMISSIONS.md.
- **Projects are hidden from people who are not assigned to them.** Someone sees a project only if they hold a role on it (or on a project above it): a role on a series covers its books, a role on one book covers that book, and a role at the whole studio does not. The Owner and an Admin see every project. A project a person cannot see is gone from the Projects tree, Home, Dashboard, Notes and Planner, from Write's list of manuscripts (even under "All manuscripts"), and from the assistant, which cannot be pointed at one by naming its folder either. A book they are on shows its series as a container. Changes to a project they cannot see are refused as if it did not exist. **Admin → People** has a **Projects they can see** list for each person. On this computer you are the Owner of your Studio, so you still see everything; the rule matters for other people once their roles are applied (Studios you only joined get it with the server). See docs/PERMISSIONS.md.
- **One ledger file per series, and a carried timeline.** A series that has a manuscript folder of its own now keeps its LitRPG and timeline ledgers once, there, with each Book's ledger inside; the Books before the one you are working on are read from the same file and put in front of it. The timeline is carried the way the LitRPG ledger was: days continue from the last Book, a Book that opens before the last one ended or a weekday that disagrees across Books is flagged, and the timeline page is drawn with the earlier Books' days. A Book that kept its own ledger before is read from it and moves into the series file the next time it is logged; a series without a folder of its own, and a book on its own, keep one file per Book as before. Chapter numbers are still each Book's own.
- **People and comparable titles on the Project page.** Associations now also lists **Comparable titles** (kept by ASIN, for the whole project or one book; a title can be a comp for several projects) and **People**: who has which role on the project (or on one book), until when, with the means to give or remove a role. This is how access is controlled: a role given on a project applies to it and its books, one given on a book applies to that book only, and the same permission check that enforces roles everywhere refuses a change someone may not make.
- **Associations on the Project page.** "What belongs to it" is now **Associations**: Market categories first, then manuscripts. Each shows whether it applies to the whole project or to one book, and a category can be assigned to a single book (it then shows in that book and in the project, not in the project's other books). It says plainly that what is assigned is what Write and Market show for the project, and where to switch to see everything.
- **A permanent page for every chapter.** When the LitRPG or timeline ledger is logged, Cadrel writes `Tracking/Chapters/Chapter N.html` for each chapter it touched: what changed, where each character stands after it, and the chapter's in-story day. The pages are self-contained HTML like the other tracker pages. A chapter whose record would not change is left alone, and a changed one keeps its old version in the project's history. `build_tracker_view` with `view: "chapters"` writes them for chapters logged earlier. Cadrel Write and Cadrel Reader now list `.html` files in the folder and show them in a read-only page viewer (scripts run in a sandbox that cannot reach the app or your files); they are never edited or deleted from there.
- **Stages belong to books.** A project (a series) no longer has a stage: its books do, each at its own. A new book starts in the first stage of the default book workflow; the Projects page shows a project's **Books** with their stages, **Close book** (to the first Done stage the gates allow) and **Reopen**. Closed books are hidden from what Cadrel shows unless you turn on **Show closed books**. A project made as a **Standalone** gets its one book automatically. A project from before keeps its stage until you remove it, and **Add first book** gives a project with a manuscript folder its first book: the folder becomes the book's (nothing is copied or moved) and the book starts in the project's stage. The workflow builder now speaks of "default for new books". File kinds say whether they belong to a series, a book or either.
- **The AI assistant understands projects and books.** Every writing tool takes a `book` as well as a `project`: name the series, and the Book when it has several (the assistant is told which to pick if it forgets). Series-level files go to the series, a Book's own work to the Book, and a closed Book can be read but not changed. `studio_projects` shows each node's level, stage and folder, and the new `studio_context` shows one series and Book whole, with the series files to read first. The outline, blurb, keywords, editing and tracker skills now work on one Book and read the series first; the series developer works at the series level; and the LitRPG tracker reads a Book's ledger with the earlier Books' in front, so a character carries on from where the last book ended.
- **Write, Market, Notes, the Planner, the Dashboard, My Books and Home now follow the project (and book) in the rail.** Write lists only that project's manuscripts (the series first, then each book), a closed book's manuscript is read-only, and an **All manuscripts** switch brings the rest back. Market shows only the categories assigned to the project, with a **Project | All** switch. The other pages have a **Project | Everything** switch, and Home lists the current project first. Finance and Files do not follow it yet.
- **A project and book scope in the rail.** The rail shows which project (and book) Cadrel is showing and opens a menu to change it; The whole app follows it (Finance and Files do not yet).

- **Invitations for readers now send people to Cadrel Reader.** The invitation message a reader receives links to Cadrel Reader's release instead of the full app, and the invitation page offers **Open in Cadrel Reader**. Invitations to edit a manuscript with its author are unchanged and still point at Cadrel. Cadrel's updater and Reader's now each read only their own releases, so one cannot be offered the other's installer.

## 0.5.0

- **A development build installs beside the stable one, on the same data.** Builds that are not of `main` now use their own app id, product name (**Cadrel Dev**), Start menu entry, shortcut, install folder and program file (`Cadrel Dev.exe`), so both can be installed and neither overwrites the other. The dev build uses the stable app's data folder (`%APPDATA%\Cadrel`), so it has the same Studios, settings, projects and Market library. Because they share data, only one can be open at a time (opening the dev build while the stable one is running says so), and a dev build that changes how data is stored changes it for the stable app too. The dev build claims no file types, so the stable Cadrel keeps opening `.md` files. The installer file keeps its `Cadrel-Setup-<version>` name, which the updater looks for.

- **Market queue: filter to new additions.** On the Queue tab, **New additions only** shows just the books that are on a category's newest list capture but were on none of its earlier captures, so after you recapture a category you can open and capture only what joined the list. New books also carry a "new" tag in the normal view, and **Open next** respects the filter. It needs a list captured at least twice; books known only from searches are never "new". The check is against any earlier capture of the same category, so a book that moved between pages or list kinds is not counted as new.

- **Six authoring skills and the tools behind them, in the AI Kit and the MCP server.** Besides the three editing passes, the kit now carries **Series Developer**, **Premise to Outline**, **Outline to Blurb**, **Outline to Keywords**, **Timeline Tracker** and **LitRPG Tracker**. Each works on its own (nothing in it refers to another skill or to any orchestration), is offered as an MCP prompt for clients without skills, and ships as a Claude skill zip, a folder for Claude Code and a `for-gpt` file. They make files in the project (`Premise.md`, `Characters/*.md`, `Outline.md`, `Marketing/Blurb.md`, `Marketing/Keywords.md`, `Tracking/…`), never in a manuscript folder. New MCP tools: `list_project_files`, `read_project_file` (in parts for long files), `write_project_file` (create, replace or append; never overwrites without `replace`, keeps the last five versions under `.cadrel/previous`, refuses manuscript and exports folders), `edit_project_file`, `check_keywords` (KDP backend keyword rules), `litrpg_log` / `litrpg_state` (an append-only mechanics ledger replayed to any chapter or in-story day, with arithmetic checks), `timeline_log` (days, quotes and chronology checks), `check_tracker`, and `build_tracker_view`, which saves self-contained HTML pages in `Tracking/` and can hand the page back to show as an artifact: a **timeline** (day ribbon, chapter-to-day map, level and XP by day, flags), a **LitRPG dashboard** (as-of-chapter slider, charts, event feed, flags) and **character sheets** that show only the values the book has given, with no notes, quotes, flags or chapter references. Not built: REST endpoints for these tools (a Custom GPT's Actions still see only the editing tools).

## 0.3.0

- **Keyword suggestions are built on a book's outline, and an AI tool can send its own.** On Market's Keywords tab, **Build on outline** lists the outline documents Cadrel finds in your projects (a file named like an outline, beat sheet, synopsis, treatment or plot plan, or kept in a folder called Outline or Plot; best guess first) and remembers your choice for the category. With one chosen, what the outline says comes first (its tropes, its genre vocabulary such as settings, creatures and jobs, and phrases it repeats), what the category's books and readers add comes next, and category phrases your outline never mentions are held back, so the five suggestions and the seven KDP strings are about *this* book while still informed by the category. Each suggestion says whether your outline backs it, and when an outline phrase is one no listed book carries it says so ("may set your book apart"). Without an outline nothing changes. **For AI tools:** the MCP server has `keyword_brief` (the chosen outline's text, the other outlines on offer, the category's signals with reasons, the words Amazon already reads, Cadrel's own suggestions, and the KDP rules) and `suggest_keywords` (single phrases and/or the seven box strings). What an AI sends lands in a separate **From your AI assistant** list on the Keywords tab, labelled with who sent it, with warnings (a word Amazon already reads, filler or a word KDP bans, a word reused across boxes) and Search, Copy and Dismiss buttons; a newer set replaces that tool's earlier one, and dismissed items stay dismissed. Nothing is searched or published for you. **It is off by default: Settings → MCP has a new Suggest keywords switch** (same rules as the file switches: applies at once, missing file means off), and a refused call tells the AI to answer in chat instead. The outline is only ever read, and the brief tells the AI to treat it as material, not instructions. Tested: outline profile, ranking with and without an outline, the injected list (limits, warnings, replacing, dismissal), both MCP tools including refusal, the service's outline choice (and that only a listed outline can be chosen), and outline discovery. Not built: outlines kept outside Write projects (a pasted outline, or the manuscripts attached to a Market book), and a different outline per book rather than per category.

- **AI tools can create and edit files in your projects, but only if you allow it (Settings → MCP).** The Cadrel MCP server gains two tools: `create_file` (a new Markdown file in a project, with any folders on its path; it never replaces a file that exists) and `edit_file` (exact-text replacements in an existing manuscript file; every edit must match one place, and if any does not nothing is changed). **Settings has a new MCP section with two switches, Create files and Edit files, and both are off by default**, so an AI app can still only read and leave review notes until you opt in. The server re-reads the setting on every change, so a switch applies at once with no restart of the AI app, and a missing or damaged settings file means everything is off. A refused call writes nothing and tells the AI to use review notes and that you can turn it on in Settings → MCP. The setting is per Studio (`ai-access.json` beside the Studio's other settings; the server is started with `--ai-access <file>`). The tools only reach manuscript files in projects (not hidden folders, not `.cadrel`, not outside the project, and not projects shared with you for review only). They are not offered by the REST API for Custom GPTs, which stays read-and-review. Tested for both permissions off, each on alone, switching during a session, no overwriting, path escapes, and all-or-nothing edits. Not built: delete or rename, and a warning if Write has the same file open with unsaved changes (an edit made on disk meanwhile may be overwritten by Write's next save).

- **The assistant can rename a Market category.** The new `rename_category` tool gives a category your own name (say "Cozy Fantasy" for Amazon's "Humorous Fantasy"); an empty name goes back to Amazon's. The name shows wherever the category is listed (the assistant's tools, the queue, My Books, exclusions) and can be used to refer to the category afterwards. The category's key does not change, so links, exclusions and notes keep working. The name is kept apart from the one Amazon gives, which every list capture rewrites, so it survives re-capturing and rebuilding the library, and it is mirrored to `user/user-data.json` like the other things you author (library schema 19). Keyword ideas and Reddit/community searches still use Amazon's own name, since that is the phrase people search for. Not built: a rename in the Market app's screens (the assistant only so far). Tested in the library (re-capture, rebuild, restoring from the user-data file, clearing, unknown category) and through the built MCP server.

- **A Market category can belong to several projects.** Until now a category could be linked to one project only (linking it to another moved it), though many books share a genre. Linking a category to a project now adds it and leaves it in the others; the project's page offers every category it does not already have, shows "also in …" for the other projects a category is in, and **Unlink** takes it out of that project only. A manuscript folder still belongs to one project and moves when linked again. A note written on a category that several projects share belongs to none of them (it is still found on the category); when the category is in one project it belongs to that one, as before. The assistant's `studio_link` tool does the same (`unlink: true` with a project removes it from that project only; with no project it leaves all of them). Existing links are unchanged. Not built: assigning one category to many projects in one step (it is one project at a time), and a category's page listing the projects it is in.

- **A KDP payment report now imports into a Studio limited to its pen names, with the Studio's part of it.** The first version of pen-name scoping left payment reports out, because a payment is one lump sum for the whole KDP account with no book or pen name in it. KDP does list each payment per sales month and source (Sales, Kindle+ Royalties), so the Studio's part is now worked out from its own sales: for each line, the Studio's royalties for that month and source (from the royalty reports and pages read it has imported, at the exchange rates the app holds) are compared with the line. If they come to nearly all of it (within 5%; 15% for Kindle+, whose rate per page KDP does not report) the Studio is the only one paid and keeps the whole line; if they come to less, the Studio keeps what they come to (accrued, tax and net scaled alike) and the rest is another pen name's; if the Studio has none for that month and source, the line is left out. The payment's own totals become the sum of what was kept. **Import the royalty and pages-read reports first, then the payment report**: the import says how many lines were estimated and lists the months it could not match, and reading the saved reports again (re-index) applies payments after all the sales, so the order of the original imports does not matter. A payment with nothing of the Studio's in it is not stored, and one imported earlier that has since lost all its lines is removed. This is an estimate: the Studio's figure for a month can be a few percent off where the app's exchange rate or Kindle+ rate differs from KDP's. KDP's monthly summary sheet is still left out of a limited library, since it has no breakdown at all. Tested with an account of three pen names (the Studio's part of a month, of Kindle+, an unmatched month, a sole pen name keeping the whole line, and re-index order), and by running the example report KDP produced against an empty library.

- **Fixed: the Windows build's smoke test failed on a port Windows had reserved.** The installed-app self-test started Market's capture server on a random port in 49000-49899, and on the GitHub Windows runners some of those ports are reserved, so binding failed with `EACCES` and the dev build was not published (dev.12 only passed on a re-run, dev.13 failed). The test now asks the OS for a free port. The app itself uses 47321 and is not affected.

- **Fixed (Windows): the minimise, maximise and close buttons did not respond to clicks** (close only flickered red when the pointer moved over it quickly). The buttons are a small view laid over the window's top-right corner, but the page underneath had a drag region there (the shell's top strip, Write's title bar, and the tab bars of Market and Finance). To Windows a drag region is the window's caption, so it took the mouse from the buttons above it. The corner is now marked as not draggable in the shell page and in every module view. I could only check this by reading the code and running the tests, not on a real Windows build, so please confirm on the next dev build.

- **Delete a book added by mistake.** A book's page in My Books has a **Delete this book** section (for roles that may archive; you type the title to confirm). It removes the book for good from everywhere the Studio keeps it: in the records, the book, its editions, the project link, every contribution, credit, right and revenue share about it or its editions, and every log entry about any of them; in Market and Finance, under each ASIN its editions had, the own-book entry, captured pages and files, imported sales, pages read, royalties, rank history, page count, splits and category exclusions. The records go first and are checked against your permission; Market is cleaned only after that. **What stays:** the project the book was made in (its manuscript is yours); KDP's payment report and monthly summary (account-wide, so they cannot be split by book); the KDP report files saved on disk, so **importing the same report again brings the book back** unless the Studio's pen names exclude it; and one log row, "a book was deleted" with who and when and no title, ASIN or ISBN, so the log still shows that records were removed. A test fills every table of a records file with a book's data and checks that no id, title, ASIN or ISBN of it remains anywhere in the file while another book, the series, people and pen names are untouched. Archiving is still the way to keep a record of a book you no longer sell.

- **Pen names belong to Studios, and a KDP import brings in only that Studio's.** A KDP report holds every author's books on the account, but pen names can belong to one Studio and not another, and people in a Studio must not see another Studio's pen names. The pen names added in Admin → People and roles are now the limit: **importing a KDP report keeps only rows whose author is one of the Studio's pen names** (matched ignoring case, accents, punctuation and "Surname, Forename" order; a "Mara Quinn and Bo Lin" byline counts if either is a pen name), and the result says how many books by which other authors were left out. **KDP's payment report and monthly summary cover the whole account** and cannot be split by author, so they are kept only when nothing in the file belongs to someone else, and the result says when they were skipped. A Studio with no pen names yet imports nothing and says to add them first. **My Books, the catalogue's "add from Market" banner, Finance and the assistant's `my_books` tool show only those pen names' books**, and a change of pen names takes effect at once (the assistant server picks the new list up when its connection is next set up). Books already in the library under other pen names are hidden, not deleted; Finance's import area offers **Remove other pen names' books** (confirmed; it removes those books with their sales, pages read and royalties and keeps your KDP files and page captures). Re-indexing applies the same limit. A computer that holds no records for the Studio (a Studio only joined) has no limit. Tested in the library (matching, rows, account-wide sheets, removal, re-index), in Market's service (live scope changes), for the pen-name list in the shell. The assistant flag is not covered by a test. Not built: a pen name's books being matched by ASIN rather than the name KDP prints, per-Studio libraries on one computer (each Studio still has its own library folder), and limiting the old manual "flag a book" list by pen name.

- **Fixed: updating and installing could be blocked by Cadrel "still running" after it was closed.** Three causes, each fixed. (1) **The assistant (MCP) server outlived the AI app that started it.** It runs as `Cadrel.exe` from the install folder, so while it ran Windows would not let an update replace that file, and the installer's check reported Cadrel as running. The server only stopped when its AI app was quit cleanly; if the AI app or its launcher was killed, the pipe closed but nothing told the server to leave. It now stops itself when its connection closes, when the program that started it is gone, on SIGTERM/SIGHUP/SIGBREAK, and (forcing exit after 3 s if closing hangs) when an update starts. The launcher inside the Claude Desktop extension also stops its server when the client goes away and whenever the launcher itself exits. (2) **An update now tells running assistant servers to leave first.** Cadrel (when it starts an update) and the installer (the first thing it does, then waits 3 s) write a marker file `.cadrel-retire` next to the program; a server that sees a recent one exits within two seconds, even if an AI app starts it again mid-update (the installer removes the marker once the new files are in; a marker older than 10 minutes is ignored). This is checked by tests that run the built server as a child process (closing stdin, the marker, SIGTERM) and by a test that the installer, the app and the server all use the same marker name. (3) **The Chrome extension was loaded from inside the install folder** ("Open the extension folder" opened `<install>\resources\extension`), so Chrome used files an update has to replace. It now opens a copy in Cadrel's data folder (`chrome-extension`), refreshed whenever the app carries a different extension version, so the install folder is never in use by Chrome. If you loaded the extension from the old place, remove it in chrome://extensions and load it again from the folder the button now opens. Also: after the windows close, Cadrel now exits within 8 seconds whatever is still winding down, so a stuck shutdown can no longer leave a process behind. If you still see processes called BookScout after this, they are the old BookScout program (or its Claude Desktop extension), not Cadrel: Task Manager → Details → right-click → Open file location shows where they live; Cadrel Market already offers to quit a program holding its port 47321.

- **Fixed: backing up and restoring a Studio lost or broke its records.** A review of the backup code found three problems, all in whole-Studio backups (a backup of one project was fine). (1) **A Studio restored as a new Studio could not open its records**: the records file keeps the Studio id it was made with, the restored Studio has a new id, so the app found no people for it and tried to start a second Studio in the same file, failing with "A role with that name already exists". A records file now keeps its own Studio id. (2) **The records were copied as the live file** (with its write-ahead log, while the app had it open), which can give a torn copy; the backup now takes a consistent snapshot (`VACUUM INTO`) and leaves out the live file and its log. (3) **The vault's working folder was not in the backup**, so work checked out and not yet checked in was lost; the `Vault` folder is now a part of the backup and comes back (the vault's versions were already in the Studio folder). Backups also record the records' schema so an older Cadrel refuses one it cannot read, and an older backup without these parts still restores. A new test backs up a Studio with a project, a task, a book, a share and a checked-out vault file, restores it under a different Studio id, and checks that everything is there; it fails without the fix.

- **Contributions, credits, rights and revenue shares** (records, service and tests; no screens until M7; migration `0010_business.sql`, Studio schema 10). Four concepts in four tables with no column or foreign key between them (a test pins that): **contribution** (who did what on a book, series, IP or edition: author, editor, cover artist, narrator…, with dates), **credit** (how a person or a pen name is named, in what role and where: cover, title page, listing…, with the name as shown and an order), **rights** (held by a person here or a named outside party; owned, licensed in or out, reverted; which right, territory, language, period, exclusive or not, restrictions in words; "in force on a date" and "an exclusive grant is out" are computed), **revenue share** (a person's share of a subject over a period, in whole basis points and whole cents, with the basis net, gross or profit and any advance). Nothing is deleted, only archived and restored; every change writes an audit row. - **The local vault, and Files** (rail, below Planner; migration `0009_file_links.sql`, Studio schema 9). Real files in a working folder (`<Cadrel folder>/<Studio>/Vault`), kept in the Studio's records and a content-addressed store of every version, under the PDM rules the server will enforce later. A file nobody is editing is **read-only on disk**. **Check out** takes it for you alone (refused while anyone holds it, including you on another computer; always starts from the newest version); **Check in** saves what is on disk as a new version with a comment and releases it (nothing changed: released with no new version); **Undo check-out** puts the vault's copy back; **Get latest** updates read-only copies and never overwrites a file you hold or a copy that was changed outside a check-out (it is reported, and you can Discard the changes); old versions can be saved as a copy beside the file, never over it. **Force release** (`vault.force`, a typed reason, a confirmation that the holder's unsaved work is not in the vault) takes a lock from someone; the holder's computer then **keeps what they had not saved next to the file** ("ch1 (lock removed 2026-11-10).md"), restores the vault's version, tells them on the Files page, and refuses their late check-in; nothing is ever deleted. **Permissions** are those of the kind of file: manuscripts (text, documents) use `manuscript.read` / `write`, art, design, fonts, audio and anything unclassified use `asset.read` / `write`; files you may not read are not listed. **References and where-used**: a file can use other files (an EPUB its manuscript and cover) at a version or the latest; "used by" is the same record read backwards and says when a user names an older version; a reference never updates itself, a person chooses. **Data cards**: a few text facts and a project per file, searchable.
